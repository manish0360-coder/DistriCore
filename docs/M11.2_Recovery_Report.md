## 1. What the requirement says, and what shipped before this

`02` §21.6:

> **NFR-AVA-001** — *"RPO ≤ 15 minutes; RTO ≤ 4 hours (DR-5)."* Verified by *"restore
> rehearsal measuring both, scheduled and recorded"*.
>
> **NFR-AVA-002** — *"Backups MUST be restore-tested on a schedule. **An untested backup
> does not satisfy this requirement.**"*

**Before M11.2 the delivered RPO was ≈24 hours.** FD-16 decided a continuous layer —
*"WAL archiving · continuous · separate local volume"* — and derived its ≈1-hour figure from
it, but no WAL configuration existed anywhere in the repository: a search for `wal_level`,
`archive_mode`, `archive_command`, `pg_basebackup`, `restore_command` and every common
archiving tool returned nothing. The nightly `pg_dump` was the only layer, so the recovery
point was the last completed dump.

Neither NFR-AVA-001 nor NFR-AVA-002 appeared in `backend/` or in any verification report.
The requirement had **no traceability at all**, which is why the gap survived ten milestones.

`03` §4.4 declared a deviation to ≈1 hour *"requires sign-off (§14)"*; `03` §14's approval
table is unsigned and `01` CF-5 still reads *"backup strategy remains provisional"*. The
Architect resolved this by **keeping the original target**, so the deviation is moot and
nothing in `01`/`02`/`03` needed amending.

## 2. The mechanism

Four pieces. Each is where it is for a reason that is about failure, not convenience.

| # | Piece | Where | Why there |
| --- | --- | --- | --- |
| 1 | `archive_mode=on`, `archive_timeout=300`, `archive_command` | `docker/compose.yml`, as server flags | Command-line flags, not a config file, so they are one fact in the file that starts the database. A consequence worth knowing: a base backup copies `postgresql.conf`, so a *recovered* cluster inherits none of them — which is why the rehearsal cluster does not try to archive |
| 2 | Local copy to a **separate** volume (`wal_archive`) | `archive_command` | FD-16's wording. `archive_command` runs inside the PostgreSQL server's shell, which has no `gpg` and no `rclone`; a network upload there would let an unreachable A-05 stall WAL recycling until `pg_wal` fills and writes stop. So it does the one thing that cannot block: `cp` to a local volume |
| 3 | Encrypt and ship, then **read the remote back** | `ops/ship-wal.sh`, every 5 min | Same host-side split `ops/backup.sh` already used (B-2: encrypted before they leave the host). The verification is the point: `rclone` exiting zero is not the claim, retrievability from A-05 is |
| 4 | Weekly physical base backup, which also owns **WAL retention** | `ops/basebackup.sh` | WAL cannot be replayed into a logical dump — PITR needs a physical anchor. And a segment stops being needed only when no retained base backup needs it, so the schedule that knows where the oldest chain starts is the only one allowed to prune |

**No pgBackRest, no WAL-G, no object-store SDK.** FD-16 alternative (c) calls them *"the
recommended Edition 2 upgrade"*; `03` §4.2 rules out a paid tier under A-19. Plain
`archive_command` plus `rclone` needs nothing that is not already installed for the nightly
dump, and the repository's own direction was explicit about this.

### The layers are separate on purpose

| Layer | Artefact | Answers | Cannot answer |
| --- | --- | --- | --- |
| Logical | `pg_dump -Fc`, nightly | *"Give me last night's database"* — restorable into any cluster, survives a PostgreSQL version change | Anything about RPO. WAL cannot be replayed into it; a logical restore starts a new timeline |
| Continuous | base backup + WAL, 5-minutely | *"Recover to 14:35 today"* | Nothing, if either half is missing |

Both are kept because they fail differently. `/healthz` reports them separately for exactly
that reason.

## 3. How 15 minutes is derived — and why a contract guards the arithmetic

```
   300 s   a committed row's segment closes            archive_timeout   (docker/compose.yml)
 + 300 s   the next shipping run picks it up           OnUnitActiveSec   (districore-wal-ship.timer)
 +  60 s   upload allowance for one 16 MB segment
 ───────
   660 s   worst-case offsite recovery point  =  11 minutes
```

Against NFR-AVA-001's **900 s**, leaving four minutes of margin.

**Both numbers are load-bearing and neither is meaningful alone.** Raising `archive_timeout`
to an hour to reduce write amplification is a one-line change that converts a met
requirement into an unmet one, and before M11.2 nothing in the repository would have
noticed. `test_recovery_readiness.test_the_rpo_budget_still_adds_up_to_less_than_the_requirement`
recomputes this sum from the three files and fails if it exceeds the target.

`archive_timeout` forces a segment switch on a quiet system, so a full 16 MB segment is
written every 300 s regardless of activity — 288 per day. GPG compresses a mostly-empty
segment to a few kilobytes, so the offsite cost is small; the local cost is bounded by
`DISTRICORE_WAL_LOCAL_KEEP_HOURS`.

## 4. How the recovery point is **observed**, not asserted

Configuration is not evidence. Three independent observables, each answering a different
question, all on `/healthz` where the A-08 monitor already polls:

| Field | Question | Source of truth |
| --- | --- | --- |
| `checks.wal_archive` | Is PostgreSQL still archiving? | **`pg_stat_archiver`** — `archive_mode`, `last_archived_time`, and `last_failed_time` *after* `last_archived_time`, which means `pg_wal` is filling and writes will eventually stop |
| `checks.wal_offsite.lag_seconds` | **How far behind is the offsite recovery point?** | The stamp `ops/ship-wal.sh` writes *only after* listing the remote back and proving every locally archived segment is present. Reported next to `rpo_target_seconds` so the endpoint states what it is measuring against |
| `checks.basebackup` | Is there anything to replay into? | The weekly base backup's verified-offsite stamp |
| `recovery_ready` | One boolean for the alert | All three of the above |

**Why three and not one.** Each link fails on its own and looks fine from the others. A
shipper stamp cannot detect a stalled archiver — *"everything local is offsite"* is a true
statement about an archive that stopped growing an hour ago. A current archive cannot detect
a three-month-old base backup, whose replay would exceed the four-hour RTO. And a fresh
nightly dump, which is what `checks.backup` reports, says nothing about any of it.

`00` §13.1 permits four alerts and no more. **No fifth channel was added**: these fields ride
the endpoint A-08 already watches, and `recovery_ready` is the single thing it has to check.

### The verification that actually discharges the requirement

`make pitr-rehearsal TARGET_TIME='…'` → `ops/restore-pitr.sh`:

1. picks the newest offsite base backup **at or before** the target;
2. decrypts it and every offsite WAL segment;
3. recovers a scratch cluster with `restore_command` and `recovery_target_time`;
4. waits for **`pg_is_in_recovery()` to go false** — not `pg_isready`, which succeeds *during*
   replay because hot standby accepts connections, and would report a recovery point earlier
   than the one achieved;
5. reports `max(audit_log.occurred_at)` — the newest business fact that survived.

**That last number is the achieved RPO.** `audit_log` is append-only (NFR-AUD-001) and
written by the application, so it is the newest state the business would get back. Row counts
— which `ops/restore.sh` reports — prove a restore happened; RPO is about how much was kept.

The rehearsal reads **the offsite copy**, not the local volume, because the local volume does
not exist in the scenario the requirement is about.

## 5. The host-loss recovery path

`docs/runbooks/restore-from-backup.md` §*Real recovery — total host loss*. In outline:
provision a host, clone the tag, restore `.env` from the password manager, fetch the newest
base backup and all WAL from A-05, recover with `recovery_target_time = 'latest'`, move the
recovered cluster into the `db_data` volume, start the stack, confirm `/healthz`.

RTO is dominated by provisioning and download, not replay. At the DR-8 envelope a week of
WAL replays in minutes; the four-hour budget is spent on the host and the network.

## 7. Residual risks, stated rather than discovered later

| # | Risk | Position |
| --- | --- | --- |
| 1 | **A failing `archive_command` fills `pg_wal` and eventually stops writes.** Enabling archiving creates this failure mode; it did not exist before | Monitored by `checks.wal_archive`, which fails when `last_failed_time` is newer than `last_archived_time` — before the disk runs out. Reported as an alert, **not** a 503: taking the service out of rotation would cause the outage sooner than the disk does |
| 2 | `archive_command` uses `cp` then `mv`, so a segment under its final name is complete, but the bytes are not `fsync`ed | Bounded and deliberate. The local archive shares a disk with the cluster it describes: if that disk is intact the file is intact, and if it is not, the authoritative copy is the offsite one, which `rclone` checksums on upload |
| 3 | **A-05 now takes continuous small writes, not one nightly file.** ~288 objects/day | Provisioning consequence, §8. `00` §277 already permits *"any S3-compatible or object store reachable by `rclone`"* |
| 4 | Media is now a **full encrypted tar** each night, replacing an incremental `rclone sync` that shipped photographs in clear from a host path that did not exist | B-2 is satisfied and the run no longer fails nightly. `04` §9 sizes media at ~24 GB after five years, at which point a nightly full upload stops being reasonable — **recorded as technical debt with a threshold**, not left implicit |
| 5 | Recovery replays into a **new timeline**, and PITR is only as good as the passphrase | S-07's rotation semantics already warn that old archives stay under the old passphrase (`docs/runbooks/rotate-secrets.md`). That applies to WAL too, and more sharply: the chain spans the rotation |
| 6 | `archive_mode` is on **in development as well** | `03` §4.3 requires development to be identical to production, and it means `make verify` exercises the archive path rather than trusting it. `make clean` and `down -v` remove the volume |

### `recovery_ready: false` in a clean environment is the correct answer

There is no A-05 in a development container, so no WAL has been verified offsite and no base
backup exists. The endpoint says so. `test_an_unprepared_host_reports_recovery_as_not_ready`
asserts exactly this, because the default posture must be *"not ready"* rather than
*"presumed fine"* — a recovery position is something that has been established, which is the
whole argument for NFR-AVA-002. **It is not an implementation failure and the fail-closed
behaviour must not be relaxed to make it green.**

The same run shows the separation working: `checks.database` and `checks.disk` are healthy,
`status` is `ok`, and readiness is independently false. A single `backup: ok` field could not
have expressed that, which is why there are now four.
