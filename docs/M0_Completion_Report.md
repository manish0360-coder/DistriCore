## 4b. Test-stage defects — second `make verify` run

Steps 1–5 passed. Steps 6 and 7 exposed four defects with **one shared root cause**.

### Root cause: the suite was not running under `config.settings.test`

The log line `django: version: 5.1.15, settings: config.settings.dev (from env)` was the
tell. `pyproject.toml` sets `DJANGO_SETTINGS_MODULE = "config.settings.test"`, but
pytest-django gives the **environment variable precedence over the ini value**, and
`compose.dev.yml` exports `config.settings.dev`.

So the suite ran against development settings: live throttles, the console SMS provider,
Argon2 hashing, django-axes enabled. Two of the five reported symptoms were consequences,
not independent bugs.

**Fix:** `--ds=config.settings.test` in `addopts`. The `--ds` flag outranks the
environment, so *any* invocation of pytest — container, CI, or a developer's shell — uses
test settings.

### 1. Throttle rates — a real defect, independent of the above

`"3/15min"` is not valid DRF. `SimpleRateThrottle.parse_rate` reads `period[0]`, so
`"15min"` yields `'1'` and raises `KeyError`. DRF supports only `second|minute|hour|day`;
there is no "per 15 minutes" rate.

Corrected to the per-IP backstops of `05` §13. **The security-meaningful limits were never
in DRF and are unchanged:**

| Limit | Where it actually lives | Tested |
| --- | --- | :-: |
| 3 OTP requests per phone / 15 min | `identity.services.request_otp` | ✓ |
| 5 attempts per code | `OtpRequest.attempt_count` | ✓ |
| 10 logins per phone / 15 min | django-axes | ✓ (config) |
| Per-IP backstops | DRF `ScopedRateThrottle` | rates validated |

Test settings now remove `DEFAULT_THROTTLE_CLASSES` rather than emptying
`DEFAULT_THROTTLE_RATES` — the latter makes DRF raise `ImproperlyConfigured` on every
scoped view.

### 2. `ConsoleSmsProvider.sent` — the canonical contract

**The canonical contract is the Protocol: `SmsProvider.send_otp(phone, code) -> None`.
Nothing else. `sent` belongs to `MemorySmsProvider` alone.**

I did **not** add `sent` to `ConsoleSmsProvider`, because that would make a provider used
in a running application accumulate **live OTP codes in an unbounded in-memory list** —
a credential store nobody asked for, readable from any stack trace or heap dump, in direct
conflict with SEC-3 and `00` §12.3.

The test suite never wanted `ConsoleSmsProvider`. It wanted `MemorySmsProvider`, which
test settings select. The defect was settings selection; the provider is correct as
written. `tests/unit/test_sms_provider.py` now asserts the boundary explicitly, so a
future change that blurs it fails a test rather than passing review.

## 4c. Third `make verify` run — two root causes, one of them a security defect

Coverage reached **87.3%** (gate unchanged at 80). Four failures remained, from two causes.

### Cause 1 — `verify_otp` rolled back its own attempt counter

**This was a live security defect, not a test artifact.**

`verify_otp` was decorated `@transaction.atomic`. On a wrong code it did:

```
otp.attempt_count += 1
otp.save(...)
raise OtpInvalid(...)          # <-- inside the same transaction
```

Raising inside an atomic block rolls the block back. **The increment was discarded every
time.** `attempt_count` stayed at 0 for ever, the FR-IAM-004 cap of five attempts never
engaged, and **an OTP could be brute-forced indefinitely** — a 6-digit code against an
unbounded number of guesses. The test was right; the implementation was wrong.

**Fix — a deliberate transaction boundary, not a decorator removal.** A failed attempt is
*committed*, and the rejection is raised **after** the block closes:

| Path | Written inside the block | Raised after |
| --- | --- | --- |
| Wrong code | `attempt_count = F("attempt_count") + 1` | `OtpInvalid` |
| Correct code, unknown user | `consumed_at` | `InvalidCredentials` |
| Correct code, inactive account | `consumed_at` | `AccountInactive` |
| No row / capped / expired | nothing | raised in-block; rollback costs nothing |

Two further corrections fell out of the restructure:

* `F("attempt_count") + 1` instead of read-modify-write, so two concurrent wrong guesses
  count as two.
* A consumed code is now committed **before** the account-state check, so a deactivated
  account cannot replay a code that was already spent. A new test pins this.

### Cause 2 — refresh rotation re-parsed the token it had just blacklisted

```
refresh.blacklist()
new_refresh = RefreshToken(token=str(refresh))   # decodes the blacklisted token
```

`BlacklistMixin.verify()` calls `check_blacklist()`, which raises `TokenError` for exactly
that jti. **Every valid refresh token therefore returned 401**, and the reuse-detection
test could never reach its second assertion.

I read SimpleJWT's own `TokenRefreshSerializer.validate` rather than guessing. Rotation
**mutates the token object in place**; it never re-parses:

```
refresh.blacklist()
refresh.set_jti(); refresh.set_exp(); refresh.set_iat(); refresh.outstand()
```

Now implemented in that order, with `outstand()` guarded by `hasattr` for 5.x tolerance.
Two tests added: that the rotated refresh token is itself usable, and that the rotated
access token authenticates — a different string is not the same thing as a working one.

### Cause 3 — the three remaining mypy `RefreshToken` diagnostics

Not a bug in our code. SimpleJWT annotates `Token.__init__(token: Token | None)` while the
parameter it actually accepts — and its only documented use — is the **encoded string**.
Verified against the installed signature. The annotation is upstream-incorrect.

The rotation fix removed two of the three call sites. The remaining construction is
wrapped in a single documented helper, `_decode_refresh()`, carrying **one** scoped
`type: ignore[arg-type]`. The codebase now contains two `type: ignore` comments in total,
both with a stated reason.

Test count **96 → 100**, all additions pinning the two defects. No test modified, no
assertion weakened, coverage gate untouched.
