## 0. Two findings that change the shape of S4.3

Both came out of reading the code, not the design. Neither was visible at v2.0.0 of the
Stage 4 review, and the first one is a **silent-defect trap**.

### 0.1 `SupplierPayment` must register as `"PAYMENT"`, not `"SUPPLIER_PAYMENT"`

`ledger.walk.annulled_entry_ids` finds an annullable target with this predicate:

```python
if entry.source_document_id is not None
and entry.entry_type == entry.source_document_type      # ← the trap
```

A supplier payment produces a ledger entry whose `entry_type` is
`SupplierLedgerEntry.Type.PAYMENT` — the literal string `"PAYMENT"`. If
`purchasing/registry.py` registered the model as `"SUPPLIER_PAYMENT"`, then
`source_document_type = "SUPPLIER_PAYMENT" ≠ entry_type = "PAYMENT"`, the entry **never
enters `unclaimed`**, the reversal `ADJUSTMENT` finds no target, and **no annulment
happens**.

The consequence is not a crash. It is the reversal becoming an ordinary positive debit
dated the day of the reversal — **precisely the "launder aged debt into new debt" defect
M6 §5A was written to prevent**, reappearing on the payables side, with every test still
green except one that specifically checks ageing.

> **Ruling required (§13, U-1):** register `SOURCE_DOCUMENT_REGISTRY[SupplierPayment] =
> "PAYMENT"`. This is **not** a change to `ledger.walk` (constraint 16 respected) — the walk
> is correct; the registry must satisfy its precondition. `GoodsReceipt` already satisfies
> it (`entry_type` and `source_document_type` are both `"GOODS_RECEIPT"`), which is why
> Stage 3 never surfaced this.
>
> **The cost, stated:** `ledger.services.SOURCE_DOCUMENT_REGISTRY` will then map **two
> models** to `"PAYMENT"` — `receivables.Payment` and `purchasing.SupplierPayment`. That is
> safe today because the registry is only ever read **forward** (model → string); grep
> confirms no reverse lookup exists anywhere. It is unambiguous in practice because
> `customer_ledger_entry` only ever references `Payment` and `supplier_ledger_entry` only
> ever references `SupplierPayment` — resolution is per-ledger, never global. **A future
> reverse lookup must therefore take the ledger as an argument**, and §13 U-2 records that.

### 0.2 `purchasing` cannot reuse the immutability base — TD-24 lands here

`receivables.models` inherits `_ImmutableDocument`, `_ImmutableQuerySet` and
`DocumentImmutable` from **`billing.models`**. The layer contract is:

```
… receivables → billing → fulfilment | field → orders | purchasing → … → inventory | ledger
```

`billing` is **above** `purchasing`, so `purchasing.models` importing it would invert the
graph and `lint-imports` would reject it. TD-24 already records the intent —
*"M6 D-7 is DEFERRED: the immutability machinery stays in `billing` until M10 hardening
rather than being moved into `core`"* — and S4.3 is where that deferral has a cost.

Options are compared at §2.2. **Recommendation: `SupplierPayment` carries its own guards**,
as `GoodsReceipt` already does, and the `core` consolidation stays a separate future step.

## 1. Recommended architecture

```
webadmin/purchasing_views.py
    GET  supplier payment form   →  mints submission_id (uuid4), renders it hidden
    POST supplier-payment-record →  passes it straight through, evaluates nothing
                │
                ▼
purchasing.services.record_supplier_payment          @transaction.atomic
    require_roles(OWNER)
    validate  →  submission lookup  →  INSERT (unique index is the guarantee)
                │                             │
                │                             └─ IntegrityError → re-read → replay path
                ▼
    ledger.services.record_supplier_entry(PAYMENT, −amount, source_document=payment)
    core.services.record_audit(CREATE, "supplier_payment")
                │
                ▼
purchasing.selectors.supplier_position               (read side, derived)
    SupplierLedgerEntry rows  →  ledger.walk.walk(policy=_SUPPLIER_POLICY)
```

**Five properties this shape delivers, each mapped to a constraint:**

| | Property | Constraint |
| --- | --- | :-: |
| 1 | FIFO comes from `ledger.walk` with a `WalkPolicy`; no algorithm is written in `purchasing` | 1 |
| 2 | Payment row and ledger entry are one `@transaction.atomic` | 2 |
| 3 | Reversal appends a compensating `ADJUSTMENT`; no historical row is edited | 3, 10 |
| 4 | `submission_id` is `NOT NULL UNIQUE`; the index, not the UI, is the guarantee | 4, 7 |
| 5 | Nothing stores what a payment settled — the position is recomputed on every read | 9 |

## 2. Data model

### 2.1 `SupplierPayment` (`purchasing`, new table `supplier_payment`)

| Column | Type | Null | Notes |
| --- | --- | :-: | --- |
| `id` | BIGINT identity | N | PK |
| **`submission_id`** | **UUID** | **N** | **UNIQUE.** Server-minted per form render. §3 |
| `payment_number` | VARCHAR(32) | N | UNIQUE. `SPY-00000001`, `nextval` — a reference, gaps permitted |
| `supplier_id` | BIGINT | N | FK → `supplier` **RESTRICT** |
| `amount` | NUMERIC(14,2) | N | **Positive.** `ck_supplier_payment_amount` (`> 0`) |
| `method` | VARCHAR(20) | N | `CASH · UPI · BANK · CHEQUE` — the `Payment.Method` set |
| `reference_number` | VARCHAR(100) | Y | `''`. Cheque/UTR number |
| `payment_date` | DATE | N | **Caller-supplied.** No `date.today()` fallback |
| `notes` | TEXT | Y | `''` |
| `paid_by_id` | BIGINT | Y | FK → `app_user` **SET_NULL** |
| `created_at` | TIMESTAMPTZ | N | |
| `is_reversed` | BOOLEAN | N | `false` — **mutable** |
| `reversed_reason` | TEXT | Y | `''` — **mutable** |
| `reversed_at` | TIMESTAMPTZ | Y | — **mutable** |
| `reversed_by_id` | BIGINT | Y | FK → `app_user` **SET_NULL** — **mutable** |

**Constraints**

- `uq_supplier_payment_submission` UNIQUE (`submission_id`) — **E3's entire guarantee**
- `uq_supplier_payment_number` UNIQUE (`payment_number`)
- `ck_supplier_payment_amount` CHECK (`amount > 0`)
- `ck_supplier_payment_reversed` CHECK (`NOT is_reversed OR reversed_reason <> ''`)
- `ck_supplier_payment_reversed_pair` CHECK (reversal fields all-null or all-set)

**Indexes** — `(supplier, -payment_date)` · `(method, -payment_date)` · `(paid_by)`

**Three deliberate differences from `receivables.Payment`:**

| | `Payment` | `SupplierPayment` | Why |
| --- | --- | --- | --- |
| Identity | `client_uuid` **nullable** | `submission_id` **NOT NULL** | M3-era callers predate `client_uuid`, so it had to be optional. This table has no history, so protection can be mandatory from the first row — and constraint 7 requires enforcement at the boundary, which a nullable column cannot give |
| `device_id` | present (M6-9, field collection) | **absent** | No offline surface originates a supplier payment (`D5_Design_Review` §2.1). A column with no writer is a column that lies |
| Immutability base | `_ImmutableDocument` from `billing` | own guards | §0.2 — the layer forbids the import |

### 2.2 Immutability — options compared

| | Option | Verdict |
| --- | --- | --- |
| **I-1** | **Own `save`/`delete` + queryset guards in `purchasing.models`, with a `_mutable_fields` set for the four reversal columns, plus a per-table trigger** | **RECOMMENDED** |
| I-2 | Move `_ImmutableDocument` to `core` now, closing TD-24 | Rejected **for S4.3**. It edits `billing` and `receivables` — Stage 1–3 code — to enable a Stage 4 feature. Moving an abstract Django base between apps should not alter migration state, but "should not" is not "does not", and the blast radius covers `invoice`, `credit_note` and `payment`. If it is wanted, it is **its own verified step**, exactly as S4.2 was |
| I-3 | No Python guard; rely on the trigger alone | Rejected. The repository's posture is layered — Python, database, and a test that attempts both. `GoodsReceipt`, `AuditLog` and `CustomerLedgerEntry` all do three |

> **TD-24 now has three call sites** (`billing._ImmutableDocument`, `GoodsReceipt`'s guards,
> `SupplierPayment`'s). That is the argument for the `core` move — recorded, not acted on.

**The trigger** is a direct analogue of `receivables/migrations/0003_payment_immutable.py`,
which is self-contained SQL and imports nothing. It keeps that migration's four rules:
DELETE refused unconditionally · everything outside the four mutable columns frozen by
`to_jsonb(OLD) − keys` comparison, **so a column added later is immutable by default rather
than mutable by omission** · `is_reversed` is one-way · a reversal without a reason is
refused.

### 2.3 What is authoritative (question G)

| Class | Fields | Rule |
| --- | --- | --- |
| **Identity** | `submission_id`, `payment_number`, `id` | Server-minted. Never caller-chosen, never edited |
| **Payment data** (authoritative, immutable) | `supplier`, `amount`, `method`, `payment_date`, `reference_number`, `notes`, `paid_by`, `created_at` | Written once. Correction = reversal + new payment |
| **Reversal state** (the only mutable columns) | `is_reversed`, `reversed_reason`, `reversed_at`, `reversed_by` | One-way, reason mandatory |
| **Derived — never stored** | supplier balance · which receipts a payment settled · ageing · open items | `SUM(amount)` and `ledger.walk`, recomputed per read (N-03/E-01, BD-1 = A) |
| **Display only** | ledger `narration` | Written once so a statement never joins to a document that may have moved |

> **No `settled` flag, no allocation column, no allocation table.** BD-1 frozen.

## 3. E3 — the idempotency mechanism

### 3.1 What is a "logical payment submission"? (question A)

> **One form render.**

Every real duplicate replays **the same rendered form**: double-click, browser Back then
resubmit, F5 on the POST result, a resurrected bfcache page. A *legitimate* second payment
requires the owner to **load the form again**.

That asymmetry is the whole design. The identity of a submission is therefore the identity
of the render that produced it — a **server-minted `uuid4` embedded as a hidden field on
GET and required on POST**. First POST consumes it; every replay presents a consumed one.

**Why not the payload?** Constraint 5 forbids `(supplier, amount, payment_date)`, and
correctly: two ₹50,000 payments to one supplier on one day is ordinary — a distributor
settling two invoices in a morning. Any natural key over payment data refuses that.

**Why not `client_uuid`?** Constraint 6, and the reason is mechanical rather than stylistic.
`Payment.client_uuid` works because **the client persists the identity across retries** —
M6-5's scenario is *"a salesman on a weak connection retrying a collection"*. A browser
persists nothing between two POSTs; a client-minted id would be regenerated on every form
render, producing a unique index that never collides — **protection in name only, and worse
than none because it looks solved.**

| | Customer collection | Supplier payment |
| --- | --- | --- |
| Origin | field app, offline-capable | web admin, online |
| Duplicate cause | **network retry** — same intent resent by the client | **human re-submission** — double-click, Back, refresh, second tab |
| Who can mint a stable id | the client, which persists it | **only the server**, at render time |

### 3.2 Where the identity lives (question B)

| | Option | Verdict |
| --- | --- | --- |
| **B-1** | **`submission_id` column on `SupplierPayment`, `NOT NULL UNIQUE`** | **RECOMMENDED** |
| B-2 | A separate submission/idempotency table mapping id → outcome | Rejected. It would hold a second record of *"this payment happened"*, which is the **"second source of payment truth"** §5A.3 criterion 7 forbids. It also needs its own expiry, cleanup and in-flight states — machinery for a question the payment row already answers |
| B-3 | Django session holds consumed ids | Rejected. Not database-enforced (criterion 5), read-modify-write races (criterion 6), and lost on session expiry. `_SENSITIVE` redacts `session` and `csrf` for a reason: these are not that |
| B-4 | Reuse `client_uuid` naming and nullability | Rejected — §3.1, and nullable cannot satisfy criterion 1 |

**B-1's quiet advantage:** a submission that *fails validation* writes no row, so the id is
unconsumed and the owner may correct and resubmit with the same one. B-2 would need an
explicit state for that; B-1 gets it from the absence of a row.

**B-1's limit, stated:** an id that was never minted is indistinguishable from one that was.
The mechanism is idempotency, **not** authentication — `login_required` and CSRF already
gate the endpoint. Recorded at §13 U-3.

### 3.3 Same identity, different payload (question C)

> **Refuse, explicitly. Never silently return, never amend.**

The owner presses Back, edits the amount, submits. They intend a *correction* — but a
payment is immutable, so there is no correction, only reversal. Two wrong answers are
available and both are plausible:

- creating a second payment → **double payment**;
- returning the original and ignoring the edit → the owner believes the edit took.

**Recommended: `ValidationFailed`, code `SUBMISSION_REPLAYED_WITH_CHANGES`**, saying the
payment already exists, quoting its number, and stating that changing it means reversing it
and recording a new one.

**Compared fields: all caller-supplied business fields** — `supplier`, `amount`,
`payment_date`, `method`, `reference_number`, `notes`. Comparison is against the **stored
payment row**, so no second copy of anything is kept.

> **Alternative considered:** compare only the financially material fields and ignore
> `notes`. Rejected — a replay whose only change is a note would then succeed while silently
> discarding the note. "Ignoring" is a quieter failure than refusing, not a smaller one.

Amounts are compared through `to_money` so `50000` and `50000.00` are the same submission.

### 3.4 Response to an identical replay (question D)

> **Return the original payment. Idempotent success, not an error.** HTTP 302 to the same
> payment detail page — the same place the first POST landed.

**Justified from this codebase, not from convention.** The established rule here is *a
repeat of an act already performed returns its result*: `reverse_payment` returns the
already-reversed payment (*"idempotent: a second reversal is a no-op, not a second
credit"*), `load_opening_balance` returns the existing entry, `record_payment` returns the
original on a `client_uuid` replay.

The behavioural argument is stronger than the consistency one: **an error makes the owner
think it failed and try again**, which is the exact behaviour that produces duplicates. An
idempotent success ends the loop.

> **This differs from S4.1, where a duplicate opening balance is *refused*, and the
> difference is not an inconsistency.** There the identity is the **supplier** — a business
> key — so a second load is a second *intent* and must be refused. Here the identity is a
> **form render** — a technical replay of one intent. Different question, different answer.

### 3.5 Idempotency state machine

```
              (no row with this submission_id)
                          │
              POST ───────┼──────────────────────────────────────────────┐
                          │                                             │
                    validation fails                              validation passes
                          │                                             │
                          ▼                                             ▼
              NO ROW WRITTEN                                     INSERT (unique index)
              id still unconsumed                                 │              │
              owner may correct and resubmit                 succeeds       IntegrityError
                                                                  │         (concurrent twin)
                                                                  ▼              │
                                                          ledger entry           │
                                                          audit row              │
                                                                  │              │
                                                                  ▼              ▼
                                                            ┌───────── CONSUMED ─────────┐
                                                            │  a payment owns this id    │
                                                            └────────────┬───────────────┘
                                                                         │
                                              replay ─────────────────────┤
                                                                         │
                                    payload identical  ──────────────────►  return the payment (302)
                                    payload differs    ──────────────────►  SUBMISSION_REPLAYED_WITH_CHANGES
```

Two states only — **unconsumed** (no row) and **consumed** (a payment owns it). There is no
in-flight state, and that is deliberate: an in-flight state would need a second table, a
timeout, and an answer to "what if the process died holding it".

### 3.7 The four submission semantics — **normative, frozen 2026-08-27**

Stated as rules rather than prose, because these four sentences are what the E3 test matrix
asserts and what a future reader must not re-derive:

> **S-1. The same `submission_id` is the same logical payment attempt.**
> One id can only ever correspond to one `SupplierPayment` row. The `NOT NULL UNIQUE`
> constraint is that statement in the schema.
>
> **S-2. A separate form render receives a new `submission_id`, and may therefore be a
> legitimate second payment.**
> Two ₹50,000 payments to one supplier on one day are ordinary. Nothing about the *payload*
> makes a payment a duplicate — only the identity does. This is why constraint 5 forbids
> `(supplier, amount, payment_date)`.
>
> **S-3. An identical replay returns the original payment.**
> Idempotent success, not an error: the same `pk`, no second ledger entry, no second audit
> row, no movement in the balance. An error would make the owner retry, which is the
> behaviour that produces duplicates.
>
> **S-4. The same id with a changed business payload is rejected explicitly.**
> `ValidationFailed`, code `SUBMISSION_REPLAYED_WITH_CHANGES`. Never silently returns the
> original, never amends it, never creates a second payment. A payment is immutable, so a
> change is not a correction — it is a reversal followed by a new payment, and the message
> says so.

### 3.6 Concurrency (question E)

Two POSTs arrive together. Both pre-check, both find nothing, both attempt the insert.

```
T1  ─ pre-check: none ─ INSERT ────────────────► committed
T2  ─ pre-check: none ─ INSERT ─ IntegrityError ─ re-read by submission_id ─ compare ─ return T1's payment
```

- **The unique index is the guarantee, not the pre-check.** The pre-check exists only to
  give the common case a clean path; the index decides the race. This is the construction
  S4.1 shipped and whose fallback was *proven* by mutation M3 — deleting the pre-check there
  still produced the correct refusal through the `IntegrityError` path.
- **The insert sits inside its own savepoint**, so the `IntegrityError` does not poison the
  outer atomic block. `record_payment` records exactly why: *"without the savepoint an
  IntegrityError would abort the whole transaction and a legitimate retry would become a 500
  instead of the original receipt."*
- **The loser writes no ledger entry**, because the entry is written *after* the savepoint
  returns. Ordering is load-bearing.
- **The loser burns a `payment_number`.** Accepted: `SPY-` is a reference drawn by `nextval`,
  gaps are permitted and expected, exactly as for `po_number`, `grn_number` and
  `payment_number`. It is not a statutory series.

## 4. Transaction boundary

```python
@transaction.atomic
def record_supplier_payment(*, actor, supplier, submission_id, amount,
                            method, payment_date, reference_number="", notes=""):
    require_roles(actor, Role.OWNER)                       # constraint 11
    # validate: submission_id present · amount > 0 · method known · payment_date present
    #           supplier active
    existing = SupplierPayment.objects.filter(submission_id=submission_id).first()
    if existing is not None:
        return _replayed(existing, payload)                # identical → return; differs → raise

    try:
        with transaction.atomic():                          # savepoint
            payment = SupplierPayment.objects.create(...)   # unique index decides the race
    except IntegrityError:
        existing = SupplierPayment.objects.filter(submission_id=submission_id).first()
        if existing is None:
            raise                                           # a different constraint fired
        return _replayed(existing, payload)

    record_supplier_entry(                                  # constraint 8
        actor=actor, supplier=supplier,
        entry_type=SupplierLedgerEntry.Type.PAYMENT,
        amount=-amount,                                     # negative: reduces the liability
        narration=f"Payment {payment.payment_number} ({payment.get_method_display()})",
        entry_date=payment_date,                            # constraint 12
        source_document=payment,                            # → "PAYMENT" (§0.1)
    )
    record_audit(action=CREATE, entity_type="supplier_payment", ...)
    return payment
```

**Everything commits or nothing does** (constraint 2). `record_supplier_entry` deliberately
carries no `@transaction.atomic` of its own — it runs in the caller's, the property Stage 3
relies on for goods receipts.

## 5. Reversal semantics (question F)

```
supplier_payment                       supplier_ledger_entry
┌──────────────────────────────┐
│ SPY-00000001                 │      ┌──────────────────────────────────────────────┐
│ amount        1000.00        │◄─────┤ PAYMENT      −1000.00   date 2026-08-02       │
│ payment_date  2026-08-02     │      │ source_document_type = "PAYMENT"              │
│                              │      │ source_document_id   = <payment.id>           │
│ is_reversed      true   ◄────┼──┐   └──────────────────────────────────────────────┘
│ reversed_reason  "cheque     │  │                        ▲
│                   bounced"   │  │                        │ annulling pair
│ reversed_at   2026-08-06     │  │   ┌────────────────────┴─────────────────────────┐
│ reversed_by   <owner>        │  │   │ ADJUSTMENT   +1000.00   date 2026-08-06       │
└──────────────────────────────┘  └───┤ source_document_type = "PAYMENT"              │
   the ONLY four mutable columns      │ source_document_id   = <payment.id>  (same)   │
                                      └──────────────────────────────────────────────┘
```

**No historical financial fact is mutated** (constraint 3). The original `PAYMENT` entry is
untouched; a compensating entry is appended. The four reversal columns are status, not
value — the same shape `Payment` and `Invoice` already use.

**Effect on FIFO ageing** (constraint 10). `annulled_entry_ids` matches the pair because
the `PAYMENT` entry has `entry_type == source_document_type == "PAYMENT"` (§0.1) and the two
amounts sum to zero. **Both leave the walk.** The goods receipts the payment had settled
therefore reappear **at their original dates**, not as fresh debt dated the reversal — the
M6 §5A defect, prevented on the payables side by the same mechanism, already proven for
supplier rows by `test_a_reversed_supplier_payment_restores_the_original_age` in S4.2.

**Service shape**, mirroring `reverse_payment`:

```python
@transaction.atomic
def reverse_supplier_payment(*, actor, payment, reason, reversal_date):
    require_roles(actor, Role.OWNER)
    # reason required
    locked = SupplierPayment.objects.select_for_update().filter(pk=payment.pk).first()
    if locked.is_reversed:
        return locked                       # idempotent: a second reversal is a no-op
    record_supplier_entry(ADJUSTMENT, +locked.amount, source_document=locked,
                          entry_date=reversal_date)
    locked.is_reversed / reversed_reason / reversed_at / reversed_by
    locked.save(update_fields=[the four])   # the trigger permits exactly these
    record_audit(action=PAYMENT_REVERSE, entity_type="supplier_payment", ...)
```

**The row lock is real**, and it locks the row this function mutates. Without it two
concurrent reversals both read `is_reversed = False` and both append a compensating entry,
crediting the supplier twice.

> **`reversal_date` is proposed as caller-supplied and required**, diverging from
> `reverse_payment`'s `timezone.localdate()`. It does **not** affect ageing — the pair is
> annulled regardless of its date — but it does affect `as_of` queries: a reversal dated
> after `as_of` correctly leaves the payment settling in that historical view. This is the
> S4.1 D3 posture (no server-clock business date). **Ruling requested — §13 U-4.**

## 6. Ledger integration and the derived position

**`purchasing.selectors`** gains the payables `WalkPolicy` and one read:

```python
_SUPPLIER_POLICY = WalkPolicy(
    adjustment_type        = SupplierLedgerEntry.Type.ADJUSTMENT,
    annullable_source_types= (SupplierLedgerEntry.Type.GOODS_RECEIPT,
                              SupplierLedgerEntry.Type.PAYMENT),
    reducing_type          = SupplierLedgerEntry.Type.DEBIT_NOTE,
    target_type            = SupplierLedgerEntry.Type.GOODS_RECEIPT,
)

def supplier_position(supplier, *, as_of=None) -> ledger.walk.Position: ...
```

- **`reduction_targets` is always `{}` in v1.0** and is passed as a literal, not queried.
  `DEBIT_NOTE` has no producer: `purchase_return` is Edition 2 (DV-8) and a posted goods
  receipt is immutable (`04` T-32). Building a query for a document that cannot exist would
  be speculative work that reads as a capability.
- **`Position` is returned directly**, not wrapped. A `SupplierPosition` with ageing buckets
  belongs to S4.4, which must also settle where the buckets live — `AGING_BUCKET_DAYS` is in
  `receivables`, **above** `purchasing`, so it cannot be reused from there. That open finding
  from S4.2 stays open and is **not** resolved here.
- `_SUPPLIER_POLICY` is the production home of the policy the S4.2 test file declared
  locally; the S4.2 test asserted only that the walk honours a second vocabulary.

## 8. Audit semantics (question H)

| Event | Audit row | Action | Entity |
| --- | :-: | --- | --- |
| Payment recorded | **one** | `CREATE` | `supplier_payment` |
| Payment reversed | **one** | `PAYMENT_REVERSE` | `supplier_payment` |
| Ledger entries (`PAYMENT`, `ADJUSTMENT`) | **none** | — | R-3 |
| Identical replay returning the original | **none** | — | nothing happened |
| Replay refused for changed payload | **none** | — | refusals are not audited here |

Both actions already exist in `AuditLog.Action`; **no enum change and no `core` migration.**

**Two payload rules, both learned the hard way:**

- **`supplier_code`, never `code`.** `core.services._SENSITIVE` matches `code` exactly, and a
  business identifier under that key silently becomes `[redacted]` — which `customers` and
  `catalogue` have been doing since M1.
- **`_SENSITIVE` also contains `token`.** This is why the field is named **`submission_id`**
  and not `submission_token`: an audit payload key of `token` would be redacted, and the one
  value worth seeing when investigating a duplicate would be the one that vanished. The id
  is not a credential and must not be named like one.

## 9. Webadmin workflow

| Route | Method | Purpose |
| --- | :-: | --- |
| `supplier-payment-list` | GET | register of payments, filterable by method and supplier |
| `supplier-payment-new` (`suppliers/<pk>/pay/`) | **GET** | renders the form **and mints `submission_id`** |
| `supplier-payment-record` | POST | consumes the id; PRG-redirects to the detail |
| `supplier-payment-detail` | GET | one payment, its ledger entry, its reversal state |
| `supplier-payment-reverse` | POST | reversal, reason required |

**The view evaluates nothing.** It mints a `uuid4` on GET, passes it through on POST, and
lets the service and the unique index decide — N-01, and the reason `webadmin` is forbidden
from importing `purchasing.models` at all.

**The form shows the supplier's current position** (`supplier_position`) before the owner
commits, which is the confirm-screen mitigation D-PUR-4 relies on for goods receipts — here
it is a **secondary** aid, because unlike goods receipts the primary guard is real.

Post/Redirect/Get after success, so a refresh re-issues the GET and mints a **fresh** id —
which is exactly why a deliberate second payment works while a replay does not.

## 11. Acceptance and test matrix (question J)

### 11.1 E3 — the six the ruling named, plus what they need to be honest

| # | Case | Expected | Notes |
| :-: | --- | --- | --- |
| E3-1 | **Sequential duplicate POST**, identical payload | one payment, one ledger entry, balance moves **once**; second call returns the *same* `pk` | the base case |
| E3-2 | **Concurrent duplicate POST** | one payment; loser returns the winner's row | must use **two real connections** (`pytest-django` `TransactionTestCase`-style / threads), not two sequential calls — a sequential test proves the pre-check, never the index |
| E3-3 | **Same supplier + same amount + same date, different `submission_id`** | **two payments**, balance moves twice | constraint 5. The test that fails a naive natural key |
| E3-4 | Same `submission_id`, **modified payload** | `SUBMISSION_REPLAYED_WITH_CHANGES`; original unchanged; **no second ledger entry** | one case per field: amount, supplier, date, method, reference, notes |
| E3-5 | **Reversal then another legitimate payment** | reversal annuls; new payment settles again; balance correct | proves reversal does not consume the ability to pay |
| E3-6 | **FIFO ageing restored after reversal** | the settled receipt reappears **at its original date**, not the reversal date | the M6 §5A defect, payables side |
| E3-7 | Validation failure leaves the id **unconsumed** | corrected resubmit with the same id succeeds | B-1's quiet advantage, asserted |
| E3-8 | `submission_id` **omitted** | refused at the service | criterion: boundary, not UI |
| E3-9 | Mutation: **drop the unique index** → E3-2 must fail | proves the index is the guarantee | the S4.1 M3 construction |

### 11.2 Payment, reversal, ledger

| Case | Expected |
| --- | --- |
| Records a payment | negative `PAYMENT` entry, `source_document_type = "PAYMENT"`, id = payment |
| Balance falls by the amount | `supplier_balance` = receipts − payments |
| Atomicity | a forced ledger failure leaves **no** payment row |
| Amount ≤ 0 refused · unknown method refused · missing `payment_date` refused | `ValidationFailed` with distinct codes |
| Only the owner may pay / reverse | `PermissionDenied` |
| Payment immutable | `save`, `delete`, `QuerySet.update`, `QuerySet.delete` all raise; the **trigger** refuses a direct SQL update |
| Reversal is idempotent | second call returns the same row, **one** `ADJUSTMENT` only |
| Reversal without a reason refused | service, CHECK and trigger all refuse |
| Un-reversing refused | trigger |
| Audit | exactly one row per act; **zero** with `entity_type="supplier_ledger_entry"`; `supplier_code` survives redaction |
| **`SupplierPayment` registered as `"PAYMENT"`** | structural test asserting `entry_type == source_document_type` for the payment entry — **§0.1's trap, pinned** |
| FIFO uses the shared walk | the existing `test_ledger_walk_boundary` contract already forbids a second implementation |

## 14. Alternatives considered — summary

| Area | Alternative | Why not |
| --- | --- | --- |
| Idempotency key | payload natural key `(supplier, amount, date)` | refuses a legitimate second payment — constraint 5 |
| Idempotency key | client-minted `client_uuid` | the browser persists nothing between POSTs; the index would never collide |
| Identity storage | separate idempotency table | a second source of payment truth; needs expiry and in-flight states |
| Identity storage | session-held consumed ids | not database-enforced; races; lost on expiry |
| Replay, identical | explicit duplicate error | makes the owner retry — the behaviour that causes duplicates |
| Replay, changed | return the original silently | the owner believes their edit took |
| Immutability | move `_ImmutableDocument` to `core` now | edits Stage 1–3 code to enable a Stage 4 feature; deserves its own step |
| Immutability | trigger only, no Python guard | breaks the three-layer posture every other financial table has |
| Settlement | allocation table / settled flag | BD-1 frozen as Option A; N-03/E-01 |
| Position | wrap in `SupplierPosition` with buckets now | speculative; S4.4 owns display and must first settle U-6 |
